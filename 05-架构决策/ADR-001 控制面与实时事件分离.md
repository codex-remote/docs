# ADR-001 控制面与实时事件分离

## 状态

已修订。HTTP 与实时传输的语义分离仍然有效，但客户端目标传输由 WebSocket 改为 HTTPS + SSE。Admin、用户、行为和 Diagnostics 由 [[ADR-005 Admin Platform 与 Relay 分离]] 确定为独立平台；可靠 Run 的数据与服务边界由 [[ADR-007 PostgreSQL 权威运行时与 Redis 实时加速]] 决定。

## 背景

系统需要同时支持可靠的任务创建/查询，以及低延迟的设备状态、日志和结果推送。纯 WebSocket 可以覆盖所有操作，但会把请求幂等、缓存、鉴权、限流、调试和断线恢复都放进自定义协议。

## 决策

- iPhone 和 `mobile-web` 使用 Run Server HTTPS API 执行登录、Run 创建、取消、快照和历史查询。
- iPhone 和 Web Client 使用 Session SSE 与 Run SSE 接收单向实时事件，断线后通过 HTTPS 快照和 `Last-Event-ID` 恢复。
- Mac Agent 的命令接收与事件上报继续使用 WebSocket Secure；客户端不连接 Agent WSS。
- PostgreSQL 的 Run 生命周期、命令 Outbox 和持久结果是事实来源；Redis 是活跃结果与实时加速层；瞬时连接不是事实来源。
- 用户资料、用户行为、技术日志、管理审计和诊断附件不进入 Relay，由 Admin Platform 分别管理。

## 结果

正向结果：命令持久化边界明确，HTTP 幂等和网关能力可复用；实时体验不需要轮询；iOS 后台断连不会影响任务可靠性。

代价：需要维护 HTTP、SSE 与 Agent WebSocket 三类契约；客户端需要分别管理 Session 和 Turn 的恢复游标；服务端必须保持读取模型与持久水位一致。

## 备选方案

- **全 WebSocket**：协议自定义工作量大，断线时命令确认语义复杂。
- **全 HTTP 轮询**：实现简单，但日志和状态延迟高、资源浪费明显。
- **iPhone 直连 Mac**：受 NAT 和移动网络限制，扩大本地攻击面。
